# Workbench maintenance

Use the fork's GitHub Issues for engineering work. Keep personal libraries, credentials, private catalogue exports, academic records, backups and borrowing details on their owner's machine. Publish only reviewed configuration, source adapters and reproducible tests using public works.

Follow the upstream repository's engineering and attribution rules. Use the installed Matt Pocock engineering skills for subsequent work: understand the existing domain and real workflow, sharpen the acceptance criteria with the owner for material product decisions, split a substantial change into independently testable issues, and implement a vertical slice using the relevant testing or diagnosis skill. Preserve the public-source URL, target edition, observed result and unresolved limitation on the issue. Use the existing issue as the sole engineering status record. Apply `to-spec` for acceptance examples, `to-tickets` and `triage` for larger changes, `tdd` and `implement` for behavior, `diagnosing-bugs` for failures and `code-review` before release.

Keep an upstream remote for bookorbit/bookorbit. The fork's deployment branch pins a released version and both image digests. Review upstream release notes, compare modifications since the pinned tag, and run acquisition, reading, export and isolated restore before changing a deployment. Use a clean instance with public samples for new-source trials and never substitute the personal collection for a test fixture. If a core change ships, build the image from the forked source, preserve legal notices, make the matching source available and record the deployed digest. Code pushes alone do not update an installed instance.
